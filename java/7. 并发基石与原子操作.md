# 并发基石与原子操作

区别于 JavaScript 的单线程事件循环，Java 是**真·多核多线程**。多个操作系统线程会同一时刻并行运行在多个 CPU 核心上，共享堆内存。

## 1. 竞态条件：为什么 `count++` 会丢数？

在多线程下，10 个线程各累加 1,000 次，结果往往只有 7,000 多。
这是因为 `count++` 在底层不是一步完成的，而是**三步操作**：
1. **读取**：从主存读出当前值（例如 5）；
2. **修改**：在 CPU 寄存器里算 5 + 1 = 6；
3. **写回**：将 6 写回内存。

当两个线程同时读取到 5，各自算出 6 写回，原本应该加 2 次的计算，实际只加了 1 次，发生了**数据覆盖丢失**！

## 2. 解决方案 A：`synchronized`（悲观互斥锁）

加锁就像给房间装了一把物理门锁。同一时刻只准一个线程进去操作，其他人都在门外挂起排队：

```java
// 方法上加 synchronized：排他锁，保证读、改、写三步合为一体
public synchronized void add() {
    count++;
}
```
- **代价**：并发高时，大量线程在门外阻塞挂起，频繁引发操作系统内核态上下文切换，开销大。

## 3. 解决方案 B：`AtomicInteger` 与 CAS（乐观无锁）

不锁门，利用现代 CPU 硬件级别的 **CAS（Compare-And-Swap，比较并交换）** 原子指令：

```java
private AtomicInteger count = new AtomicInteger(0);

public void add() {
    count.incrementAndGet(); // 硬件 CAS 指令：原子自增
}
```

- **CAS 心智模型（乐观对账）**：
  1. 我先看一眼现在是 5，准备改成 6；
  2. 写回时拿着旧值 5 去问 CPU：“现在内存里还是 5 吗？如果是，立即帮我改成 6；如果已经被别人捷足先登改成 7 了，放弃这次修改”；
  3. 修改失败也不阻塞，自己立马**自旋重试**（拿新的 7 算成 8 再去试）。

核心铁律：并发多线程下绝对不能裸跑普通累加；轻量数值计数选 `Atomic`（无锁 CAS 高性能），复杂多步业务控制选锁。
