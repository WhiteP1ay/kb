# Spring AOP 与事务

AOP（面向切面编程）的本质就是**在不改动核心业务代码的前提下，把日志、事务、鉴权等横切杂活抽出来，以代理拦截器的形式无侵入外挂到方法外围**。

## 1. 前端类比：Koa 洋葱模型与 Axios 拦截器

AOP 最核心的注解是 **`@Around`（环绕通知）**，执行模型与 Koa 的 `await next()` 几乎 100% 对齐：

```java
@Around("execution(* com.example.service.*.*(..))") // 拦截哪些方法（切点表达式）
public Object logAround(ProceedingJoinPoint joinPoint) throws Throwable {
    System.out.println("1. 前置：记录请求时间");

    Object result = joinPoint.proceed(); // 👈 等同于 await next()！喊门卫放行执行原业务

    System.out.println("2. 后置：计算总耗时");
    return result; // 必须将业务返回值递交给调用方
}
```

- **`execution(...)` 切点表达式**：本质就是 **Java 里的 CSS 选择器**，用来精准圈定要拦截哪个包、哪个类的哪个方法。
- **通知时机（生命周期钩子）**：
  - `@Before` / `@AfterReturning` / `@AfterThrowing`：被动小挂件，Spring 负责调原方法。
  - `@Around`：主动总代理，手握 `joinPoint.proceed()` 全权决定原方法跑不跑、跑几次、返回什么。

## 2. 声明式事务 `@Transactional` 的底层秘密

`@Transactional` 表面是一个注解，底层就是一个官方内置的 `@Around` 切面：
在 `proceed()` 前开启事务（`BEGIN`），正常跑完提交事务（`COMMIT`），一旦抓到异常立即回滚（`ROLLBACK`）。

## 3. 经典死穴：为什么同类 `this.` 调用会让事务失效？

```java
@Service
public class OrderService {
    public void createOrder() {
        this.pay(); // 💥 致命陷阱：这里的 this 是没有穿 Proxy 代理外衣的裸奔真身！
    }

    @Transactional
    public void pay() { ... }
}
```

- **底层本质**：Spring AOP 的所有超能力全都在动态生成的 **Proxy（替身壳子）** 上。
- 外部调用 `orderService.createOrder()` 走的是 Proxy 替身；但在 `createOrder` 内部执行 `this.pay()` 时，**`this` 永远指向堆里的真身对象自己**！
- 真身调用真身，根本没有走外面的 Proxy 壳子，开启事务的逻辑完全被绕过，事务彻底失效！
- **解法**：职责拆分，将 `pay()` 移到独立的 `PaymentService` 中注入调用；或者把 `@Transactional` 加在外层的 `createOrder()` 上。

核心铁律：`execution` 是方法的 CSS 选择器；`@Around` 必须显式 `proceed()` 放行；同类内部 `this.` 自调用必然绕过 AOP 代理导致事务失效。
