# Spring 数据访问与 JPA

持久层负责将内存中的 Java 对象与关系型数据库打通。理解底层通信链条、实体建模规范与关联查询陷阱，是构建健壮后端的核心。

## 1. 持久层架构底座链条

```text
你的业务代码 → Spring Data JPA (极简动态代理仓库) → Hibernate (ORM 实现引擎) → JDBC (底层网络驱动) → 数据库
```

- **JDBC (Java Database Connectivity)**：Java 官方最底层的数据库通信规范（对标 Node.js 的原生 `pg` / `mysql2` 驱动），负责建 TCP 连接、发原始 SQL 字符串、接收行集 `ResultSet`。
- **JPA (Jakarta Persistence API)**：Java 官方的 ORM 接口标准规范（相当于 TypeScript `interface`），只定义规则与标准注解（`@Entity`、`@Table`），自己不干活。
- **Hibernate**：JPA 规范的默认实现引擎，幕后真正将对象操作翻译成 SQL 语句的打工人。
- **Spring Data JPA**：Spring 基于 JPA / Hibernate 封装的**运行时动态代理库**。你只管声明空接口，Spring 在内存里动态合成实现类并注册为 Bean。

## 2. 实体建模与规范模板

```java
@Entity                         // 告诉 JPA 这是一个数据库映射类
@Table(name = "orders")         // 映射物理表名 orders
public class Order {

    @Id                         // 主键
    @GeneratedValue(strategy = GenerationType.IDENTITY) // 自增主键 (对应 SERIAL / AUTO_INCREMENT)
    private Long id;

    @Column(nullable = false)
    private BigDecimal amount;

    @Transient                  // 关键：瞬态字段，业务内部临时使用，JPA 绝不建列也不存取
    private String tempToken;

    // 【避坑铁律】必须保留无参构造器！
    // Hibernate 从数据库捞出数据时，必须靠反射无参构造器 new 实例后再灌值
    public Order() {}

    // Getter / Setter 略...
}
```

## 3. 动态代理与派生查询（方法名即 SQL）

只要声明接口继承 `JpaRepository<实体类, 主键类型>`，开箱自带全部基础 CRUD（`save`, `findById`, `findAll`, `deleteById`）。

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    // Spring 启动期通过 PartTree 解析器做 AST 语法分析，将方法名自动翻译成 SQL 并预编译缓存：
    // SELECT * FROM orders WHERE status = ? AND amount > ?
    List<Order> findByStatusAndAmountGreaterThan(String status, BigDecimal minAmount);

    // 跨关联对象查询：findBy + 关联实体属性名(User) + 对方主键(Id)
    // SELECT * FROM orders WHERE user_id = ?
    List<Order> findByUserId(Long userId);
}
```

- 💡 **启动期校验机制**：若实体中不存在方法名中的属性（如手滑写成 `findByNonExistField`），Spring Boot 在启动的第一秒直接抛 `PropertyReferenceException` 崩溃，绝不拖到运行时暴雷。

## 4. 关联关系与 Jackson 循环引用排雷

### 视角法则（口诀）
> **“站在当前类，看对方属性”**：
- `Order` 里持有单个 `User`（多个订单对应一个用户）→ 贴 **`@ManyToOne`**；
- `User` 里持有 `List<Order>`（一个用户对应多个订单）→ 贴 **`@OneToMany(mappedBy = "user")`**。

### 循环引用爆栈惨案与 DTO 铁律
```java
// 错误示范：Controller 直接将含双向关联的 Entity 丢给前端
@GetMapping("/orders/{id}")
public Order getOrder(@PathVariable Long id) {
    return orderRepository.findById(id).orElseThrow();
}
```
- **惨案根因**：Spring 转 JSON 的工具（Jackson）会盲目反射调用所有 `getter`。`Order` 取 `user`，`User` 取 `orders`，深层递归无限套娃，瞬间打爆线程栈内存抛出 **`StackOverflowError`**。
- **LAZY 无法阻断的原因**：`FetchType.LAZY` 是给数据库优化的（按需查库），但 Jackson 调用 `user.getOrders()` 时会强制唤醒懒加载代理，甚至在 Session 关闭时抛出 `LazyInitializationException`。
- **解法铁律**：**永远不要将 Entity 直接暴露给前端！** 必须通过专用的 **`OrderResponseDTO`** 提取扁平数据后输出，从物理上切断循环链条。

## 5. JPA vs MyBatis 核心权衡

| 维度 | Spring Data JPA (Hibernate) | MyBatis / MyBatis-Plus |
| :--- | :--- | :--- |
| **设计哲学** | **全自动 ORM（面向对象）** | **半自动 SQL 映射（面向 SQL）** |
| **SQL 编写** | 框架自动生成，业务面向对象思维 | 开发者手写 SQL 于 XML / 注解 |
| **核心优势** | 单表与中小型 CRUD 研发极速，DDD 标配 | 复杂报表、海量多表 JOIN 深度调优，SQL 零黑盒 |
| **适用场景** | 敏捷交付、海外企业、企业中后台、领域驱动设计 | 国内互联网大厂、高并发交易、复杂数据分析与大屏 |

核心铁律：实体类无参构造是命根子；关联注解按当前类视角定单双（多对一用 `@ManyToOne`）；对外吐数据死守 DTO 防循环引用爆栈；单表通用交给 JPA，极限制定大 SQL 找 MyBatis。
