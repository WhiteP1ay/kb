# 请求幂等

## 是什么

请求幂等是指：客户端发送一次请求与连续发送多次相同请求，对服务端产生的**预期效果相同**。

幂等不代表每次响应必须相同，也不代表资源不会被其他请求修改。判断重点是当前请求重复执行后，是否继续改变服务端状态。

## HTTP 方法的幂等性

| 方法 | 标准语义是否幂等 | 说明 |
|---|---|---|
| GET | 是 | 读取资源，不应修改资源状态 |
| PUT | 是 | 创建或整体替换指定资源，重复执行后最终状态相同 |
| DELETE | 是 | 重复删除后，资源最终都处于不存在状态 |
| PATCH | 不保证 | 是否幂等取决于补丁内容和接口设计 |
| POST | 不保证 | 重复执行通常会多次创建资源或触发操作 |

## GET

```http
GET /users/1
```

两次请求可能因为用户数据被其他操作修改而返回不同内容，但 GET 请求本身没有修改资源，所以仍然幂等。

## PUT

PUT 通常表示使用请求内容创建或整体替换指定 URI 的资源：

```http
PUT /users/1

{
  "name": "Tom",
  "age": 20
}
```

执行一次和执行多次，用户最终都会被设置为相同内容，所以 PUT 按标准语义是幂等的。

## DELETE

```http
DELETE /users/1
```

第一次请求可能返回 `204 No Content`，第二次可能返回 `404 Not Found`，但最终状态相同：用户 1 不存在。

因此，响应状态码不同不影响 DELETE 的幂等性。

## PATCH

PATCH 表示对资源进行部分修改，本身不保证幂等。

设置固定值通常是幂等的：

```json
{
  "name": "Tom"
}
```

执行多少次，名字最终都是 Tom。

基于当前值进行运算通常不是幂等的：

```json
{
  "operation": "increment",
  "amount": 10
}
```

执行一次增加 10，执行两次增加 20。

## POST

```http
POST /orders
```

重复执行通常会创建多个订单，因此 POST 默认不保证幂等。不过可以通过幂等键、业务唯一索引等机制，让具体的 POST 接口实现业务幂等。

## 常见误区

- 幂等不等于每次响应内容相同
- 幂等不等于每次响应状态码相同
- 外部数据发生变化，不代表 GET 失去幂等性
- HTTP 方法具有标准语义，但实际接口仍可能被错误实现
- PATCH 和 POST 不是一定不能幂等，而是标准不保证它们幂等
